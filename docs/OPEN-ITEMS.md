## How the page behaves, and process notes

- **S13-5 - Screen readers hear a whole screen again on navigation and on a re-render.** `#stage` in `index.html` is `aria-live="polite"`, so replacing its contents announces the new content. Taps that keep a screen's shape are patched in place and are not announced (DECISIONS S13-7), but moving to the next screen, and a tap that opens a follow-up question, replace the contents. The live region could be narrowed (for example to a short "step N of M" line) when S15 touches `index.html`; it was not changed here because `index.html` is not an S13 file and the existing screens rely on the behaviour. Not tested with an actual screen reader, only with the accessibility tree, keyboard and focus checks in the Browser pane.
- **S14-1 - Listen to the umbrella screen once with a real screen reader.** The drawing is a labelled section with an ordered list, the bars and icons are hidden from assistive technology, and the one-line status element (`#stk-live`) is the only thing announced when an answer changes a verdict, with the redrawn stack set to `aria-live="off"` because `#stage` is a polite live region. That follows the ARIA rules and was checked in the accessibility tree and with focus in the Browser pane, but it was not heard (no screen reader is available to the build). Worth a minute with VoiceOver on the umbrella screen and the action list before launch; if the stack is still read out in full on each tap, narrow `#stage`'s live region instead (see S13-5).
- **S14-4 - Print in black and white relies on the words and the icon shapes.** The fills keep their colours in print and become greys on a black-and-white printer; the status sentence and the icon outline carry the meaning. Looked at with the print rules applied as a screen style, not on paper.
- **S13-7 - The action list was read at 375px, as OPEN-ITEMS S9-2 asked.** The longest items (sewer, flood, the dorm renters item) are long but readable, each paragraph is short, and the sources are small text. They were deliberately not collapsed: the sources are what make the list credible when read aloud to an agent, and a collapsed block would not print or be easy to reach by keyboard. If the owner still wants less scrolling, shorten the Background in the flag files first.
- **S13-10 - Goldens record real flag copy.** Any change to the copy of a flag that fires in one of the 32 browser scenarios fails that scenario until it is re-recorded; that is intended (DECISIONS S13-9, R1-12). Re-record only the affected scenarios, check the diff with the method in `tests/browser/README.md`, and never edit a golden by hand.
- **R1-5 - Replaying the browser goldens loads a few dozen module files per scenario.** A plain `python3 -m http.server` can drop connections when three scenarios start at once, so the harness loads a scenario up to three times and defaults to three scenarios at a time (`tests/browser/README.md`). If that is ever flaky in another environment, run `pool=1`; a bundle for the test page would remove the cause but adds a build step the site does not have.
- **S12-4 - Adding a flag now touches several tables on purpose.** A new flag needs a scenario that triggers it (`tests/scenarios/scenarios.mjs`), a row in `tests/audit/spec-checklist.test.mjs` (which SPEC line it implements), an entry in `REQUIRES` in `tests/audit/households.test.mjs` (which policies it is about) and, if it is a Drop, the policy table in `tests/audit/flag-content.test.mjs` and `tests/audit/coverage.test.mjs` and a rule in `tests/audit/evidence.mjs` saying what already covers it (DECISIONS S12-8). A flag that breaks one of the audit rules is fixed in the same change, whichever story wrote it: there is no allow-list (DECISIONS S12-10). A flag whose text depends on several answers also needs its variants reached by a scenario (`tests/audit/coverage.test.mjs` names them; `tests/audit/variants.mjs` says which variant a household's answers call for). The failure messages name what is missing. The root `README.md` ("Changing the content") lists these steps (Story S16).
