# Decisions and spec deviations

Append-only log. Each entry: what was ambiguous or changed, what was decided, why. Review these first.

- **D1 - Q1 option list is wider than the spec's Q1 sentence.** The spec's Q1 lists Auto, Home, Renters, Umbrella, Health and five Other items, but later sections need Motorcycle, Boat, and Towing/roadside to be selectable "in Q1". The derived `policies` set therefore includes motorcycle, boat and towing (see ARCHITECTURE adapter table).
- **D2 - Added a "which credit cards do you carry" question.** The spec says to cross-reference the card table and name the card, and to flag stronger when a held card carries the benefit; that needs to know the cards. Asked once, only when a card-linked Other item is held, as a closed list of cards in the table plus "other / none".
- **D3 - Card tranche is "roughly a dozen".** The spec names 8 starting cards ("Chase Freedom" and "Amex Blue Cash" being product families). The table expands families to their current products and adds benefit-rich popular cards to reach about 12. Final list in `research/cards-*.mjs`.
- **D4 - Analytics provider is pluggable and defaults to `none`.** The spec picks Plausible, Fathom or Zaraz without choosing one; no account exists yet. The adapter supports all three; the owner sets one in config.
- **D5 - Environment: no Node.** Unit tests run under macOS `jsc` via `scripts/test.sh`; the pure core is runtime-agnostic. UI behavior is verified in the Browser pane against recorded goldens.
- **D6 - Repository and base (revised 2026-10-10).** The owner chose to build on the existing Coverage Check app in `brentshiely/insurance-optimizer` ("this is a better version"), extending it rather than starting a new app. Work is committed to `main` of that repo, one commit per story. A scratch repo `brentshiely/insurance-overlap-explainer` was briefly created holding only the superseded first bootstrap; it is unused and can be deleted by the owner.
- **D7 - Hosting/analytics accounts are not touched.** Pushing to `main` does not deploy. `npm run deploy` (live site coverage-check.pages.dev) and analytics account setup are owner actions.
- **D8 - Gate questions on within-policy exclusions.** For sewer backup and flood, the wizard first asks (yes / no / not sure) whether the coverage is already on the policy and only raises the Question item for "no" or "not sure", so informed users are not nagged. The spec's "each surfaced as a Question item" is preserved for everyone who is or may be exposed.
- **D9 - The spec's "does not ask for the user's state" vs the host app's state picker.** The host app asks for a state and has state-driven findings; those stay. The new overlap engine is state-neutral: it never receives or branches on state and never names one, as the spec requires of its flags.
- **D10 - The engine ignores policy-screen numbers.** The host's per-policy fields are editable sample defaults (the page says "Editable sample data") and cannot be distinguished from user input. The engine therefore asks its own closed-list questions, with "Not sure", for every figure it needs (e.g. liability limits in the umbrella branch) rather than trusting those fields. This can duplicate a question for users who also edited the policy screen; accepted for honesty.
- **D11 - Jet ski / RV / ATV / E-bike are not in the overlap v1 scope.** The spec defers RV, ATV and jet ski as fast-follow and lists only motorcycle and boat. The host's existing powersports findings still handle all of them.
- **D12 - Modules, not a single file.** The inline script and styles move to `public/js/app.js` (ES module) and `public/css/app.css` so the logic is testable and CSP-friendly. The page therefore needs to be served over http(s) (it already is on Cloudflare Pages and via `npm run preview`); opening `public/index.html` straight from disk no longer works because browsers block module scripts on `file://`.
- **D13 - The existing app's commercial sources are left alone.** `app.js` cites some commercial/secondary sources (e.g. ValuePenguin, Progressive, Policygenius, AgentSync). The overlap spec's neutrality rule applies to the new flags; existing citations are listed in `docs/OPEN-ITEMS.md` for the owner rather than changed.
- **S2-1 - Condition DSL is strict.** `evaluateCondition` rejects empty `all`/`any`, extra keys, mixed forms, and an `answer` without exactly one of `is`/`in`/`includes`, and checks the whole tree before evaluating. Why: an authoring slip (e.g. `all: []`, which would be vacuously true) should fail loudly in tests, not silently show or hide a question. `env` is `{ answers }`, not a bare answers object, so passing the wrong thing throws instead of giving a wrong boolean.
- **S2-2 - Visibility edge cases.** (a) A `showIf` that references a question that is itself hidden hides the question, including inside `not` (the ARCHITECTURE rule, applied literally). (b) A reference to a question that does not exist hides the question at runtime (the wizard must not crash on an authoring bug) and is a hard error in `validateCatalog`. (c) A condition cycle throws at runtime and is a hard error in `validateCatalog`.
- **S2-3 - Answer normalization.** `prune` (and every read in the session) first sanitizes answers: unknown option ids, wrong shapes and non-question keys are dropped; multi answers are put in option order and deduplicated; an exclusive option wins over the others; an empty multi answer is "unanswered". Reason: a stale or hand-edited answer must not gate other questions, and equivalent inputs must produce byte-identical results. `policies` is the one reserved non-question key; it is sorted and deduplicated. `setAnswer`/`toggleOption`/`clearAnswer` validate ids (throw on unknown) but do not prune other answers, so flipping a gate back and forth keeps what the user entered; `evaluate` prunes.
- **S2-4 - `not_sure` on multi questions is exclusive.** The appended option is `{ id:'not_sure', label:'Not sure', exclusive:true }` for multi questions (plain `{ id, label }` for single). "Not sure" cannot sensibly be combined with a real selection. `exclusive` on option data (e.g. "None of these") has the same meaning.
- **S2-5 - Flag contract refinements.** `applies` may return `true` as shorthand for `{}`; `undefined` (a forgotten `return`) throws rather than silently never firing. `priority` is optional with default 100 (validated as a finite number when present) so a missing priority cannot break ordering or block a parallel story. `title` is templated exactly like `background`/`ask`/`reason`. Text returned by a function also goes through `{{token}}` resolution so a leftover token is always an error. Evaluation errors name the flag and field.
- **S2-6 - Context details.** `ctx.option(qid)` returns an array of option objects for multi questions (a single object for single). `ctx.answer('policies')` is `undefined`; use `ctx.holds`. The ctx, its answers and options are frozen so flag code cannot corrupt the catalog. `ctx.cardsWith(key)` counts only `primary`, `secondary` and `yes`; `unverified` and `none` never count (SPEC: unverified is never stated as fact). `ctx.cards()` reads the multi question with id `cards`; each option names its card via `value.cardId`, falling back to the option id with `_` changed to `-` (question/option ids are snake_case, card ids kebab-case). Validation checks that every `value.cardId` exists.
- **S2-7 - Validation scope beyond the story list.** Also checks: condition form vs question type (`includes` only on multi, `is`/`in` only on single), policy ids in `holds` against the adapter's list, `domain` from the closed list (flags and questions), `section` is snake_case, `id === key` for sources and cards, all six card benefit keys present (use `unverified` when unconfirmed), non-empty text fields, malformed `{{ }}` templates in static strings, and impossible dates (e.g. 2026-02-30). `cards` is optional in the catalog; `sources` is required. An https URL must have a dotted host (so `https://localhost` fails).
- **S2-8 - Two internal engine modules.** `engine/constants.mjs` (closed lists, reserved ids) and `engine/util.mjs` (clone/freeze/compare helpers) are shared by the engine files; they are pure and covered by the same source-scan test. The story lists six engine files plus the stub; these are additions, not changes to any contract.
- **S2-9 - Data module export shapes are part of the contract.** `data/catalog.mjs` imports named `QUESTIONS`, `SOURCES`, `CARDS` and the default array of each flag file; stories S3b, S4b, S5 and the flag stories keep those shapes. Documented in ARCHITECTURE "Parallel build rules".
- **S2-10 - Test infrastructure added.** `tests/fixtures/catalog.mjs` (small fake catalog; its `example.org` URLs are reserved documentation domains, never shown to users), `tests/helpers/purity.mjs` (deep freeze, copy, property-read recorder), and `tests/engine/purity.test.mjs`, which scans the module graph reachable from the engine and the catalog for forbidden globals and imports (skipped where jsc's `read()` is unavailable). Tests were mutation-checked against a scratch copy: breaking pruning, transitivity, the id tie-break, template checking, cycle detection, https checking, `not_sure` appending, the adapter's read set, or input purity each makes the suite fail.
