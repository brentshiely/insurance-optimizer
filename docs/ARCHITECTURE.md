# Architecture

How Coverage Check is built. `docs/SPEC.md` is the product spec and the only definition of the product. The earlier prototype was discarded (DECISIONS D15); its handoff is archived at `docs/archive/coverage-check-prototype-handoff.md` for history only. The site is deployed from `public/` to Cloudflare Pages (project `coverage-check`). Whoever changes a contract updates this file in the same commit. `docs/TRACEABILITY.md` maps every requirement of the SPEC to the code and the tests that carry it, and says which are deferred or deviate (and why); `README.md` says how to run, test and change the project.

## What the product is

The page is the flow in SPEC "Question flow and branching" and nothing else: an entry screen, Q1 ("Which policies do you have?"), one screen for each question section that the ticked policies open, and the insurer action list (Raise / Drop / Question, each with Background, Ask, one-line Reason, Source). It has two parts:

- **The pure overlap engine** (`public/js/overlap/`): the decision tree, the flags, the liability stack, the source registry and the credit-card table. Plain data in, plain data out.
- **The page** (`public/index.html`, `public/css/app.css`, `public/js/app.js`, `public/js/overlap-ui/`): a thin shell and a small ES module that keeps two things in memory, the answers and the screen index, and draws the screens the view-models describe.

There is no state picker, no per-policy numbers to type, no document or photo upload and no telemetry panel. Every question is a pick from a closed list, so nothing is typed, nothing is uploaded and nothing is derived from another screen.

## Principles

- **Guarded by goldens.** A browser golden master (`tests/browser/`) replays scripted journeys through the real page and fails when a screen's text, a control's state or the order of screens changes. Goldens change only deliberately (`tests/browser/README.md`, "Re-recording").
- **No AI/LLM at runtime.** Fixed decision tree; identical answers give byte-identical output.
- **No personal data stored or sent.** No cookies, `localStorage`, `sessionStorage`, IndexedDB, URL/query/hash state, or network calls carrying answers. Answers live in memory only. Analytics (S15) sends only closed-list labels.
- **Pure core.** Everything under `public/js/overlap/` is pure ES2022: no DOM, no Node APIs, and none of `URL`, `console`, `setTimeout`, `structuredClone`, `fetch`. It runs unchanged under macOS `jsc`, Node, and browsers. Only `public/js/app.js` and `public/js/overlap-ui/**` touch the DOM, and of those only `app.js` reaches for a browser global: the `overlap-ui` modules take the elements and browser objects they need as arguments, so they load and are tested under `jsc` too.
- **State-neutral.** The page never asks for a state, and no flag branches on one or names one (SPEC "Sources and authority"). Copy refers generically to "your state's department of insurance".
- **The engine reads only answers to its own closed-list questions.** Q1 ("Which policies do you have?") is one of them, and every other question offers a closed list, usually with a "Not sure" option. Nothing is typed, nothing is derived from another screen, and there are no silent defaults.
- **Every flag is sourced.** A flag with no resolvable source fails validation and the suite. Sources follow SPEC "Sources and authority" (non-commercial; no insurer/agency/comparison sites).
- **Zero build, zero dependencies** for the site. `wrangler` stays a dev dependency used only by `npm run deploy`, which this work never runs.

## Environment and testing

- This machine has **no Node**. Unit tests run under macOS JavaScriptCore: `scripts/test.sh [path-substring]` (also `npm test`; falls back to Node if present). Runner: `tests/harness.mjs` (`test`, `suite`, `assert`, `assertSnapshot`, `serialize`). Synchronous tests, `tests/**/*.test.mjs`, auto-discovered.
- jsc has **no `URL`, `console`, `fetch`, `structuredClone`**; it has `print` and `read(path)`. Pure modules and tests must not use them.
- Data modules are `.mjs` with `export default <plain data>` (never `.json`) so tests can import them.
- **Browser tests.** Serve the repo root with a plain static server (`python3 -m http.server <port> --bind 127.0.0.1`; the page is at `/public/index.html`) and open `tests/browser/golden.html` in a browser tab that is in front (a hidden tab is throttled). `tests/browser/golden.html` replays scripted scenarios through the real page in a same-origin iframe, compares each screen's text (`#stage`, `#known` and the progress value) with recorded goldens, and writes `GOLDEN: PASS` or `GOLDEN: FAIL ...` into `<pre id="result">` (read it with `get_page_text`): it starts as `GOLDEN: RUNNING` (poll until it changes), then its first line is exactly `GOLDEN: PASS` or `GOLDEN: FAIL <scenarioId> step <n>` (step 0 = initial load, step k = after the k-th entry of the scenario's `steps`); a filtered run (`?only=`) reports `GOLDEN: PASS-PARTIAL`, which is not a full pass. Nothing on the page is volatile, so nothing is normalized. Scenarios are plain data in `tests/browser/scenarios.mjs`; goldens are `tests/browser/golden/<id>.mjs`. `tests/browser/golden-shape.test.mjs` (jsc) checks their shape, their coverage of the catalog and the invariants of the flow without a browser.
- Snapshots (mechanism built by S6, `tests/snapshots/README.md`): `tests/snapshots/*.snap.mjs` (`export default <plain data>`), compared with `assertSnapshot`. Each snapshot has a generator `tests/snapshots/gen/<name>.gen.mjs` that prints the data as JSON with `print()` (via `serialize()` from the harness, so key order is stable), usually built by a function in `tests/snapshots/builders/` that the test also calls. `scripts/update-snapshots.sh [--check] [name]` runs every generator under jsc and writes the matching `.snap.mjs`; regenerate only deliberately, and any snapshot diff must be explainable by the story. S12 adds `scenario-flags` and `scenario-texts` over the scenario matrix (see "Scenario matrix and audits (Story S12)" below).
- `npm run deploy` publishes the live site. **Never run it.** Pushing to `main` does not deploy.

### Scenario matrix and audits (Story S12)

`tests/scenarios/scenarios.mjs` is the scenario matrix: named households `{ id, answers }`, where `answers` is a plain answers object exactly as the page keeps it (Q1 `policies` plus a tap on a closed list for every question those ticks open). A scenario is **canonical** (`session.prune(answers)` returns it unchanged, so Q1 is in the question's order and nothing answers a hidden question) and **complete** (every visible question is answered, as the page requires before the action list). The matrix as a whole ticks every policy, chooses every option of every question and answers Not sure to every question that offers it. It triggers every flag, across all three buckets.

`tests/audit/*.test.mjs` audit the whole catalog and run in the normal suite (`scripts/test.sh audit` for just these):

**How the shell loads the page.** `index.html` holds markup and metadata only. It links `css/app.css` in `<head>` and loads `js/app.js` with `<script type="module">` at the end of `<body>`. Both paths are relative, so the site works with `public/` as the web root (Cloudflare Pages, `npm run preview`). Module scripts need http(s): the page does not work from `file://`. There is no inline script, no `<style>` block and no `style="..."` attribute (the progress bar's width and the hidden field used to copy text are set through the browser's style API, which the policy allows), so the Content-Security-Policy needs no `'unsafe-inline'` (DECISIONS R1-8).

## Core data contracts

### Answers
Plain JSON `{ [questionId]: optionId | optionId[] }`: the one input of the engine (`evaluate(answers)`, `createContext(answers)`, the session and every view-model function). There is no other state and no adapter: the page keeps this object and nothing else.

Q1 is an ordinary asked answer. `answers.policies` is the list of policies the user ticked in the first question, "Which policies do you have?" (`data/questions/policies.mjs`, id `policies`, a multi question that is always shown, has no Not sure and ends with an exclusive "None of these"). Its option ids are exactly the policy ids the `holds` condition and `ctx.holds` accept (`POLICY_IDS`): `auto`, `home`, `renters`, `umbrella`, `health`, `motorcycle`, `boat`, `rental_car`, `towing`, `travel`, `phone`, `warranty`, `accidental_death`, in the SPEC's order. Every later question appears only when the policy or item it is about was ticked there. Gates read Q1 through `{ holds: id }` and `ctx.holds(id)`, which are true when `id` is a policy id (`POLICY_IDS`) that the answer includes; they never match the exclusive `none`, so "None of these" holds nothing. No gate reads `policies` as an ordinary `answer` condition (a test enforces it).

Single questions hold one option id, multi questions an array. Unanswered = key absent. `'not_sure'` is the reserved option id for "Not sure". Only closed-list option ids exist; no free text anywhere.

Pruning (`session.prune`, run first by `evaluate`) returns a new answers object holding only valid answers to visible questions: unknown option ids, wrong shapes (array for a single question, string for a multi) and keys that are not questions are dropped; a multi answer is put in the question's option order, deduplicated, an exclusive option (e.g. "None of these", `not_sure`) wins over the others, and an empty multi answer counts as unanswered. Q1 gets no special treatment: it is pruned like every other multi question (so `policies` is stored in the SPEC's order, not sorted), and it counts in `meta.answeredCount`. Ticking "None of these" means no policies at all, so every downstream answer is pruned.

### Question
```js
{
  id: 'auto_liability',            // snake_case, unique
  domain: 'core'|'umbrella'|'auto'|'home'|'renters'|'health'|'vehicles'|'deductible'|'other'|'cards',
  section: 'start'|'umbrella_stack'|...,   // which wizard screen groups it (final list under "Question catalog (S5)")
  type: 'single'|'multi',
  prompt: 'What is the most your auto policy will pay ...?',
  help: 'Where to find this / why we ask (plain language)',   // optional
  options: [{ id: '250_500', label: '250/500', value: { perPerson: 250000, perAccident: 500000 }, exclusive?: true }],
  allowNotSure: true,              // engine appends { id:'not_sure', label:'Not sure' }
  showIf: Condition | null,        // null = always shown (subject to its section being shown)
}
```
Option `value` carries machine-comparable data (numbers or `{min,max}` bands); labels are display only.

Details fixed by S2 (`engine/session.mjs`, `engine/validate.mjs`):
- `createSession(catalog)` resolves each question into a deep-frozen copy; with `allowNotSure` it appends `{ id:'not_sure', label:'Not sure' }` (for `type:'multi'` also `exclusive:true`). Authors never list `not_sure` themselves (validation rejects it). Conditions may refer to `not_sure` only on a question with `allowNotSure`.
- `exclusive: true` on a multi option means picking it clears the other options and picking another clears it (e.g. "None of these").
- `domain` is one of the `DOMAINS` list in `engine/constants.mjs` (the ten values above). `section` is a snake_case string. Question and option ids are snake_case (option ids may start with a digit, e.g. `250_500`, `1m`). `showIf` may be omitted (same as `null`).
- The multi question with id **`cards`** is the card question (`CARDS_QUESTION_ID`). Each of its options names a card via `value: { cardId: 'chase-sapphire-preferred' }`; an option without `value.cardId` falls back to its id with `_` turned into `-`. Non-card options (e.g. "None of these") simply match no card. Validation checks every `value.cardId` exists in `cards`.

The full plan, including the question-to-flag contract for S6 to S11, is `docs/QUESTION-FLAG-PLAN.md`; its tables are checked against the catalog by `tests/data/questions.test.mjs`.

Contract details fixed by S5:
- **Sections.** `SECTIONS = [{ id, title, reason, showIf }]` in display order; `id` is the `section` of its questions, `reason` is plain text tied to what the user already told us in Q1 (the first section, `start`, holds Q1 itself, so its reason says why the question comes first), `showIf` is a Condition over policies (`holds`) or `null`. No section gate reads an answer other than through `holds`. Questions of one section are contiguous in `QUESTIONS`. Every question carries its own complete `showIf` (the engine never reads sections); the tests prove a section has a visible question exactly when its `showIf` is true. The host (S13) renders one `ovl:<section>` screen per section with a visible question.
- **`policies` (Q1)** is the first question, always shown. Its options are the SPEC's list in the SPEC's order (`auto`, `home`, `renters`, `umbrella`, `health`, `motorcycle`, `boat`, `rental_car`, `towing`, `travel`, `phone`, `warranty`, `accidental_death`) followed by an exclusive `none` ("None of these"); it has no Not sure. The renters label also covers "one you pay for so a child living away from home, like at college, has coverage", so the SPEC's headline Renters + Homeowners case (a parent who owns their home and pays for a student's renters policy) is reached by ticking Home and Renters; there is no separate tick for it (DECISIONS S5-15 replaced by R1-4). Flags about that case read `ctx.holds('home')` and `renters_for`.
- **Option `value` shapes.** A number (whole dollars: `umbrella_limit`, `home_liability`, `umbrella_min_home`); a split limit `{ perPerson, perAccident }` (auto-style presets 100/300, 250/500, 500/500, used by `umbrella_min_auto`, `umbrella_min_motorcycle`, `umbrella_min_boat`, and, with an extra first rung `lower` "Lower than 100/300" whose value is the largest limit it can mean, `{ perPerson: 99999, perAccident: 299999 }`, by the user's own `auto_liability`, `motorcycle_liability`, `boat_liability` and `auto_um_uim_limit`; `home_liability` likewise gets a first rung `lower` "Lower than $300,000" = 299999, while the umbrella-minimum questions have no `lower` rung); or a band `{ min, max }` (`umbrella_exposure`, `auto_value`, `deductible_*`, `emergency_cushion`). Bands are whole dollars with both ends inclusive, `max: null` is open ended, the first starts at 0 and the next `min` is the previous `max` plus one. Inside a question every option has the same shape, and Not sure never has a value (flags check `ctx.isNotSure(qid)` first). Compare band edges, never a guess: "certainly below" is `a.max !== null && a.max < b.min`; a deductible exceeds the cushion when `cushion.max !== null && deductible.min > cushion.max`.
- **`cards`** uses a static list: `CARD_CHOICES` (12 `{ id (kebab-case), name }`, exported from `questions/cards.mjs`) plus an exclusive `other_none`. Option ids are the card ids with hyphens turned into underscores, which is how `ctx.cards()` maps them back, so the options carry no `value.cardId` while `CARDS` is empty (`validateCatalog` rejects a `cardId` not in `CARDS`). S4b/S11b verify the ids against `CARDS`.
- **Not sure.** Offered on every question except `policies`, `side_business`, `auto_financing`, `renters_for` and `cards` (reasons in DECISIONS S5-8).
- **Gates.** A gate refers only to questions earlier in display order (a test enforces it). Because visibility is transitive, a question that reads another question's answer is hidden whenever that question is hidden, so gates only read questions that are visible whenever the reader should be: `auto_gap_coverage` and `auto_collision` read `auto_financing` and `auto_value` (always visible with an auto policy), `auto_um_uim_limit` reads `auto_um_uim`, `renters_child_housing` reads `renters_for`, and `card_usual_payment` reads `cards`. A gate must never reference two questions that can be hidden for different users (the user would then never see it), which is why `renters_for` is the single root of the renters chain: it is visible exactly when Renters is ticked in Q1, and the follow-up needs only `holds('home')` and `renters_for` is `child_away`. A `holds` read counts as a read of Q1 for visibility and for cycle detection; Q1 is always visible, so it hides nothing.

### Condition DSL (data, serializable)
```
{ holds: 'auto' }                           // Q1 (`policies`) ticks this policy id
{ answer: 'qid', is: 'optId' }              // single
{ answer: 'qid', in: ['a','b'] }            // single, any-of
{ answer: 'qid', includes: 'optId' }        // multi
{ answered: 'qid' }
{ all: [c...] }  { any: [c...] }  { not: c }
```
A question is visible iff its `showIf` is true AND every question its `showIf` references is itself visible (transitive). `evaluate()` prunes answers to non-visible questions first, so stale answers never leak into results.

Built behavior (`engine/conditions.mjs`):
- `evaluateCondition(cond, env)` with `env = { answers }` (the answers object; Q1 is `answers.policies`). Returns a boolean. `holds` is `holdsPolicy(answers, id)` (also exported): true only for a policy id in `POLICY_IDS` that `answers.policies` includes, so a ticked `none` or an unknown id never matches. `is`/`in` match only single (string) answers, `includes` only multi (array) answers, `answered` is true for any non-empty answer including `not_sure`; unanswered or inherited keys are never matches.
- Malformed conditions throw an `Error` ("Malformed condition: ...") naming the path of every problem. The whole tree is checked before evaluating, so a bad branch is reported even if an earlier branch would short-circuit. Rejected: non-objects, empty objects, unknown forms, extra keys, `answer` without exactly one of `is`/`in`/`includes`, non-string ids, empty `in`, empty or non-array `all`/`any`.
- Also exported: `checkCondition(cond) -> string[]` (problems, never throws) and `conditionRefs(cond) -> { answers: [{ qid, form, optionIds }], holds: [policyId] }`, used by the session and by validation.
- Session visibility rules: a reference to a question that does not exist hides the question (validation reports it); a `holds` condition counts as a reference to the `policies` question, so a catalog without Q1 hides every question whose gate uses `holds` (validation reports that too); a condition cycle throws "Condition cycle between questions: a -> b -> a" (validation reports it first). A `not` gate whose referenced question is hidden is hidden too (transitivity wins).
- Session API (`createSession(catalog)`): `questions`, `getQuestion(qid)`, `isVisible(qid, answers)`, `visibleQuestions(answers)`, `prune(answers)`, `setAnswer(answers, qid, value)`, `toggleOption(answers, qid, optionId)` (multi only), `clearAnswer(answers, qid)`, `nextUnanswered(answers, section?)`. The three change helpers return new objects, never mutate their input, throw on unknown question or option ids, and deliberately do not prune other answers (so a user flipping a gate back and forth keeps what they entered; `evaluate` prunes). `nextUnanswered` returns the first visible, unanswered question in catalog order (optionally within one section) or `null`.

### Source (registry entry) - required fields
```js
{ id:'iii-umbrella', publisher:'Insurance Information Institute', title:'...', url:'https://...', lastVerified:'2026-10-10' }
```
All four required; `url` https (with a dotted host); `lastVerified` a real `YYYY-MM-DD` date (month and leap years checked). `data/sources.mjs` exports the registry as a **named** `SOURCES` object keyed by source id, with `id === key`.

**Sources (built by S3b).** `public/js/overlap/data/sources.mjs` holds the registry: 89 entries, one per distinct URL, sorted by id, built from every `verification.status: "verified"` source in the five non-card research files (`research/*.mjs`; the 101 research entries collapse to 89 because S3a already gave a repeated page one id everywhere, so no id was merged or remapped). Each entry has exactly `id`, `publisher`, `title`, `url`, `lastVerified` (the research's `authorityType` and `verification` fields stay in `research/` and are not shipped). A flag cites a source by putting its registry id in `sourceIds`; `evaluate` turns each id into a `{ id, publisher, title, url, lastVerified }` entry on the result flag, and `validateCatalog` fails any id that is not in `SOURCES`. Flag authors pick ids from the Sources tables in `research/INDEX.md` (or the facts' `sourceIds`), never invent one, and never write a URL into a flag. Only authority hosts from SPEC "Sources and authority" appear (iii.org, naic.org, insureuonline.org, fema.gov, floodsmart.gov, irs.gov, healthcare.gov, cms.gov, hhs.gov, dol.gov, ftc.gov, consumerfinance.gov, federalreserve.gov, insurance-research.org, consumerfed.org, kff.org, including subdomains), and none of the commercial insurer, agency or comparison sites. `tests/data/sources.test.mjs` enforces the shape, unique ids and URLs, both host lists, that the registry equals the verified research sources field for field, that every research fact's `sourceIds` resolve, and that the real catalog passes `validateCatalog`. To add a source: verify it, add it to the right research file (and `research/INDEX.md`) first, then add the same entry here. Credit-card sources live in `data/cards.mjs` (`guideUrl`), not here.

### Flag
```js
{
  id: 'umbrella-home-below-required-min',   // kebab-case, unique
  domain, bucket: 'raise'|'drop'|'question',
  alternateBuckets?: ['question'],           // optional: other buckets applies() may file this flag in (see below)
  kind: 'cross-policy'|'within-policy'|'education',
  priority: 10,                              // lower sorts first within bucket; ties by id
  title: 'Raise your home liability to your umbrella\'s required minimum',
  applies(ctx): false | null | { emphasis?: 'normal'|'strong', bucket?: 'raise'|'drop'|'question', vars?: {name: string|number} },
  background: string | (ctx, vars) => string,
  ask:        string | (ctx, vars) => string,
  reason:     string | (ctx, vars) => string,
  sourceIds: ['iii-umbrella', ...],          // >= 1, each must exist in SOURCES
}
```
Strings may contain `{{var}}` tokens resolved from `vars`; an unresolved token is an error. `applies` is pure and deterministic.

Built behavior (`engine/evaluate.mjs`, `engine/render.mjs`, `engine/validate.mjs`):
- `title`, `background`, `ask` and `reason` are each a non-empty string or `(ctx, vars) => string`, all handled the same way (so `title` may also use `{{var}}`). A function's returned text also goes through token resolution, so a token left in it is an error. Tokens are `{{name}}` (name = letters, digits, underscore, not starting with a digit; spaces inside the braces allowed); values must be strings or finite numbers; format numbers into strings yourself. Malformed tokens (`{{}}`, `{{a b}}`, stray `{{`/`}}`) are errors.
- `applies(ctx)` may return `false`, `null`, `true` (shorthand for `{}`) or `{ emphasis?, vars? }`. Returning `undefined` (a forgotten `return`), a string or an array throws, naming the flag. `emphasis` defaults to `'normal'`.
- `bucket` in the `applies` result files this household's item in a bucket other than the flag's own (Story S12, DECISIONS S12-9). It must be the flag's own `bucket` or one listed in its `alternateBuckets`, otherwise evaluation throws, naming the flag; with no `bucket` the flag's own is used. The flag's declared `bucket` is its usual home (what the plan and the SPEC checklist list); the result flag carries the bucket it was filed in and is sorted with it. `alternateBuckets` is optional, validated as a non-empty list of different valid buckets that excludes the flag's own, and only three flags use it today: rental car, travel insurance and extended warranties are declared `drop` with `alternateBuckets: ['question']`, because the SPEC makes them a Drop only when something already covers the same thing (below).
- `priority` is optional (a finite number; default 100 when absent). Lower sorts first.
- Errors while evaluating a flag are rethrown with the flag id (and field) in the message. A flag that does not apply is never rendered, so only flags that fire can hit render errors; `validateCatalog` catches the static problems earlier.
- `domain` must be one of the question `domain` values; `kind` one of `cross-policy | within-policy | education`.

### Context (`ctx`)
`ctx.holds(policyId)` (a policy ticked in Q1; see "Answers"), `ctx.answer(qid)`, `ctx.is(qid, optId)`, `ctx.includes(qid, optId)`, `ctx.isNotSure(qid)`, `ctx.option(qid)` (chosen option object, `.value` available), `ctx.cards()` (selected CARDS entries), `ctx.cardsWith(benefitKey)`, `ctx.stack` (LiabilityStack model or null). Reading a non-visible/unanswered question returns `undefined`/`false`; it never throws.

Built behavior (`createContext(answers, catalog = default)` in `engine/evaluate.mjs` builds the same ctx that `evaluate` passes to flags; it prunes first). The ctx and everything it hands out are frozen, so a flag cannot alter answers or the catalog by accident.
- `ctx.answer(qid)`: the option id (single) or array of option ids (multi); `undefined` for unanswered, hidden or unknown questions. `ctx.answer('policies')` is Q1's array like any other multi answer (prefer `holds`, which also ignores the exclusive `none`).
- `ctx.is(qid, optId)` is for single questions and `ctx.includes(qid, optId)` for multi; each is `false` for the other kind.
- `ctx.isNotSure(qid)` is true when the answer is `not_sure` (single) or includes it (multi).
- `ctx.option(qid)`: single -> the chosen option object (with `.value`, or the `{ id:'not_sure', label:'Not sure' }` option); multi -> an array of the chosen option objects; `undefined` when unanswered. Check `isNotSure` before reading `.value`.
- `ctx.cards()`: the card entries chosen in the `cards` question (see Question), ordered by card id, as frozen copies; `[]` when none. `ctx.cardsWith(benefitKey)`: those whose `benefits[benefitKey].status` is `primary`, `secondary` or `yes`. `unverified` and `none` never count; a flag that wants to mention an unverified benefit must read `ctx.cards()` itself and never state it as fact.
- `ctx.stack`: `computeLiabilityStack(ctx)`, run once while the ctx is built (`ctx.stack` is `null` during that call). `null` unless the user holds an umbrella; otherwise the LiabilityStack model below, frozen with the ctx. Flags read it through `stackFindings(ctx.stack, type)` (exported by `engine/liabilityStack.mjs`, safe on `null`).

### Results
```js
evaluate(answers) -> {
  flags: { raise: ResultFlag[], drop: ResultFlag[], question: ResultFlag[] },
  stack: LiabilityStack | null,
  meta: { visibleQuestionIds: string[], answeredCount: number }
}
// ResultFlag: { id, bucket, domain, kind, title, emphasis, background, ask, reason,
//               sources: [{ id, publisher, title, url, lastVerified }] }   // text fully rendered
```
Ordering: bucket, then `priority` ascending, then `id`. Same answers => deep-equal results.

Built behavior: `evaluate(answers, catalog = default catalog)` (`engine/evaluate.mjs`). All three buckets are always present (possibly empty). `meta.visibleQuestionIds` is in catalog order and `answeredCount` counts visible questions with a valid answer. `sources` are fresh copies with exactly the five fields, in `sourceIds` order. The result is built from fresh objects, so callers may mutate it. Input answers and catalog are never mutated (tests deep-freeze both). `stack` is a copy of `ctx.stack`.

`engine/validate.mjs`: `validateCatalog(catalog) -> { ok, errors: string[] }` (never throws; reports every problem) and `assertValidCatalog(catalog)` (returns the catalog, or throws one `Error` listing all problems). Beyond the contract it also checks: option ids unique per question and never an explicit `not_sure`; every `showIf` well formed, referencing existing questions and option ids, a form that matches the question type (`is`/`in` single, `includes` multi), known policy ids in `holds`, and no cycles (a `holds` gate is an edge to Q1; a catalog that uses `holds` must contain the `policies` question, and that question must be a multi question that is always shown, has no Not sure and whose ordinary options are policy ids); id conventions (questions/options snake_case, flags/sources/cards kebab-case); flag `domain`, `kind`, `bucket`, optional `alternateBuckets`, optional numeric `priority`, text fields, `applies` a function, `sourceIds` non-empty and existing; `id === key` for sources and cards.

### Health and deductible flags (built by S10)
`data/flags/health.mjs` (4 flags) and `data/flags/deductible.mjs` (3 flags) are all Question-bucket flags in the S10 priority range 410 to 470. They never judge plan adequacy and never ask for a typed number. Conventions other code can rely on:
- **Firing rule per flag** (details in DECISIONS `S10-2` to `S10-7`): a flag never fires on an unanswered question; Not sure is handled flag by flag as `docs/QUESTION-FLAG-PLAN.md` says (the MedPay and supplemental flags fire on it with its own wording, the HSA, short-term and deductible flags do not, except that a Not sure cushion fires the deductible flags at normal emphasis when the deductible band starts at $1,000 or more).
- **Deductible-vs-cushion** compares band edges only (`deductible.min > cushion.max`; a `5000_plus` cushion never fires). `strong` emphasis means the bands prove the deductible is above the cushion; `normal` means it could be (cushion Not sure) or, for the other flags, the default. The flag text mentions band labels only.
- **Open-enrollment wording** lives in one place: `flags/health.mjs` exports the named `OPEN_ENROLLMENT_NOTE` and `OPEN_ENROLLMENT_SOURCE_IDS`, and `flags/deductible.mjs` imports them for its health flag. A flags file may export named helpers like this; the default export stays the array `flags/index.mjs` reads. The sentence is health-only: the auto and home deductible flags never use it, and it carries its plan year (OPEN-ITEMS `S10-1`).
- **Dated copy** (a plan year, an "As of" month, an HSA threshold year, the Federal Reserve survey year) is always written with its date in the text so it stays true when read later; the files that hold it are listed in OPEN-ITEMS `S10-1`.

### Card (`data/cards.mjs`)
Keyed by card id: `{ id, name, issuer, lastVerified, guideUrl, benefits: { rentalCar, tripProtection, cellPhone, extendedWarranty, purchaseProtection, roadside } }`, each benefit `{ status: 'primary'|'secondary'|'yes'|'none'|'unverified', summary, conditions? }`. `unverified` is never presented as fact. The UI always tells users to check their own card's current benefits guide. The shipped table is empty on purpose: the card research is deferred (DECISIONS D14), so every card sentence in the product is generic until it is filled (OPEN-ITEMS S16-7 has the steps, S16-8 the re-verification process).

Validation (S2): `data/cards.mjs` exports a **named** `CARDS` object keyed by card id (`id === key`, kebab-case); `name`, `issuer` non-empty, `lastVerified` a real date, `guideUrl` https, and `benefits` must contain all six keys above (use `status: 'unverified'` for anything not confirmed from the issuer's guide), each with a valid `status`, a non-empty `summary` and optional string `conditions`. Extra benefit keys are allowed if they have the same shape. The `cards` catalog part is optional for validation.

Drop or Question (Story S12, DECISIONS S12-9). The SPEC defines Drop as coverage the household pays for twice, so `other-travel-insurance-overlap` and `other-extended-warranty-overlap` are filed as a Drop only when a ticked card is confirmed to have the benefit in the table AND `card_usual_payment` is `yes` (exactly the condition for strong emphasis, so a Drop is always strong), and `other-rental-car-waiver` only when the household has a car policy it has not said lacks collision and comprehensive, or a ticked card the table lists as paying first AND `card_usual_payment` is `yes`; otherwise each is a Question about what would pay. While the real card table is empty, travel and warranties are therefore Questions for every household. A Drop never says the cover may be worth buying; the Question may. A reason mentions "my card" only when the household ticked a card. `tests/audit/evidence.mjs` holds the same rules apart from the flags, and the audits check both directions.

How flags use the card table (S11, `data/flags/other.mjs`). A flag reads cards only through `ctx.cards()` and `ctx.cardsWith(benefitKey)`. A card whose benefit status is `primary`, `secondary` or `yes` is named, with the table's own `summary` and `conditions` and the date it was last checked; `unverified` (or a missing key) becomes "check whether <card> includes this in its current benefits guide" and is never stated; `none` is not mentioned. With no table entry for a held card the wording is generic ("if you carry a credit card, check its current benefits guide"), no card is named and emphasis stays normal. Emphasis is strong only when a held card has a confirmed benefit and the user says they usually pay with their cards (`card_usual_payment` is `yes`); a Not sure or missing answer never raises it. `card_usual_payment` and `phone_bill_on_card` do not say which card the user pays with, so a flag never puts a named card in the user's mouth: "one of these cards" appears only when every ticked card is named, otherwise the text says the benefit helps only if the card they use is a named one, and the phone strong ask and reason are conditional on the bill being on the named card (DECISIONS S11-8). Every text that mentions a card ends with the card-freshness caution (`CARD_CAUTION`, exported by `other.mjs`; the card work in OPEN-ITEMS S16-7 replaces it with `CARD_DISCLAIMER`). A flag's text that cites an organisation names it in full with a one-clause gloss at the first mention ("National Association of Insurance Commissioners (NAIC, a group of state insurance regulators)"), and the copy test fails on any acronym that is not defined where it first appears (DECISIONS S11-7). Generic card wording makes no claim about what a card's benefit requires; only the table's own `summary` and `conditions` do. A flag's `sources` list holds registry sources only, so a card's own guide link is not part of a result flag (OPEN-ITEMS S11-2). Tests inject `tests/fixtures/otherCards.mjs` (five invented cards, "Fixture Card Alpha" and so on, keyed by real card ids so the unmodified `cards` question maps to them) into a copy of the catalog; they never assert a real card claim.

### LiabilityStack (built by S6)
One engine, `computeLiabilityStack(ctx)` in `engine/liabilityStack.mjs`, builds the model that flags consume as `ctx.stack` and that the Story S14 visualization (`js/overlap-ui/stackView.mjs`, see "Liability stack drawing (S14)" below) renders as `results.stack`. It is plain, self-describing data (labels, statuses, numbers, one sentence per layer; no functions, no `undefined`, nothing shared between calls) and reads only the user's own closed-list answers, never a number typed anywhere, because nothing is typed (DECISIONS S6-1).

**When it exists.** `null` unless `ctx.holds('umbrella')` (or when `ctx` is not an evaluation context). With an umbrella and no underlying policy it is the umbrella alone (`layers: []`).

```js
{
  version: 1,
  umbrella: { id: 'umbrella', label: 'Umbrella', limit: 1000000 | null, limitLabel: '$1 million' | 'Not sure' | 'Not answered yet', limitAnswer: 'known' | 'not_sure' | 'unanswered' | 'unreadable' },
  layers: [   // one per held underlying policy, always in the order auto, home, motorcycle, boat
    {
      id: 'auto', label: 'Auto liability', policyText: 'auto policy',
      limitShape: 'split' | 'single',                        // auto, motorcycle, boat are split; home is a single amount
      limit: { perPerson, perAccident } | number | null,     // dollars; null unless limitAnswer is 'known'
      limitLabel: '100/300',  limitText: '100/300',          // as shown in the question / ready for the middle of a sentence ("lower than 100/300")
      limitIsCeiling: false,                                 // true only for the "Lower than ..." rung
      limitAnswer: 'known' | 'not_sure' | 'unanswered' | 'unreadable',
      required: { ... } | number | null,  requiredLabel, requiredText, requiredAnswer,   // what the umbrella asks for underneath, same shapes
      status: 'ok' | 'below_required' | 'above_required' | 'unknown',
      statusLabel: "Meets your umbrella's requirement" | "Below your umbrella's requirement" | "Above your umbrella's requirement" | 'Not confirmed',
      shortBy: null | number | { perPerson, perAccident },   // exact difference, only when below_required and the limit is exact
      summary: 'Your auto liability limit is 100/300, but your umbrella asks for 250/500.',
    },
  ],
  counts: { ok, below_required, above_required, unknown },   // number of layers in each status
  findings: [   // what flags consume, in layer order
    { id: 'auto-below-required', type: 'below_required' | 'above_required' | 'unconfirmed', layer: 'auto', layerLabel, policyText,
      limitLabel, limitText, limitIsCeiling, requiredLabel, requiredText, notSure: [] | ['limit'] | ['required'] | ['limit', 'required'] },
  ],
  attachmentNote: 'An umbrella pays only after the liability limit on the policy underneath has been used up, ...',
  sourceIds: ['iii-what-is-umbrella-liability-policy', 'iii-should-i-purchase-umbrella', 'iii-homebuyers-handbook'],   // sources for attachmentNote; look them up in SOURCES
}
```

**Attachment point.** An umbrella pays only after the liability limit of the policy underneath has been used up (research fact `umbrella-attaches-after-underlying-exhausted`; it adds to the underlying policy and does not replace it). So the *attachment point* of a layer is that layer's own liability limit (`layer.limit`): the amount of that policy's coverage that has to be used up before the umbrella can start to pay for that policy. For a split limit like 250/500 there are two: per person and per accident. The *required minimum* (`layer.required`) is the attachment point the umbrella insurer expects, as the user read it off their umbrella; each insurer sets its own (research fact `umbrella-underlying-requirements-insurer-specific`). The model compares the two. It deliberately says nothing about what an umbrella insurer does in the stretch between a limit below the requirement and the requirement itself, because no authoritative source states it (DECISIONS S3a-umbrella-1, S6-2), and it adds no "total protection" figure for the same reason.

**Status.** `ok`: the limit equals the requirement. `below_required`: the limit is certainly lower (for a split limit, lower on either number). `above_required`: not below, and higher on either number. `unknown`: the limit or the requirement is Not sure, unanswered or unreadable, or a ceiling cannot be placed against the requirement. A "Lower than ..." answer is a ceiling (`limitIsCeiling`): its `limit` is the largest limit the rung can mean (299,999, or 99,999/299,999), so it is `below_required` against every requirement the catalog offers and `unknown` against anything at or under the ceiling. Not sure never gives a verdict: it gives `unknown` and an `unconfirmed` finding naming which part is Not sure (`notSure`). Unanswered gives `unknown` and no finding. The umbrella's own size does not change any layer.

**Findings are what flags read.** `below_required` feeds the four Raise flags, `above_required` (auto and home only) feeds the over-buying Question, and `unconfirmed` feeds the Not sure Question; see `docs/QUESTION-FLAG-PLAN.md` S6. Other exports: `stackFindings(stack, type)`, `STACK_STATUSES`, `LAYER_IDS`, `LOWER_OPTION_ID`, `STACK_VERSION`.

**Inputs.** Per layer, the matching pair of questions: `auto_liability` / `umbrella_min_auto`, `home_liability` / `umbrella_min_home`, `motorcycle_liability` / `umbrella_min_motorcycle`, `boat_liability` / `umbrella_min_boat`; the umbrella object reads `umbrella_limit`. The first rung (id `lower`) of each limit question is the ceiling convention (DECISIONS S5-13).

**Markup and behaviour.** Three files in `js/overlap-ui/` and `js/app.js`.

Just a few taps about what you have, with nothing to type and nothing to upload."), how it goes, the not-advice note, the privacy line and **Get started**. `overlapScreenHtml(sections, screenId, backHtml, stackVm?)` is one `ovl:<section>` screen: a "Step N of M" eyebrow (Q1's says only "Step 1", because how many steps follow depends on what is ticked there), the section title as `<h2 id="ovl-heading" tabindex="-1" data-focus>`, the reason, one group per visible question, a hint (Q1's says to tick a policy or None of these; the others mention Not sure) and a Continue button that is disabled until every visible question on the screen is answered. A question is a `role="group"` named by its prompt (`aria-labelledby`) and described by its help text; a Yes / No question uses `.qrow` + `.yn2`, anything else `.chips` (`chips stack`, one per line, when a label is long); every option is a `type="button"` toggle with `class="sel"` AND `aria-pressed`, carrying `data-oq="<questionId>" data-ov="<optionId>"`. `actionListHtml(vm, counting, stackVm?)` is the `Your insurer action list` section (`<h2 id="al-h" tabindex="-1" data-focus>`, counts, intro, the `INFO_NOTE` not-advice note, Copy / Print buttons and the `role="status"` line `#al-status`, then a group per bucket with an `.item` per flag: bucket tag in text, title, Why it matters, What to ask, Say this, Source(s) as "publisher, linked title (https only, `target="_blank" rel="noopener"`, visually hidden "(opens in a new tab)"), last verified date", `Higher priority` for `emphasis: 'strong'`), the honest empty state (no buttons) and the privacy line. `actionsFootHtml(backHtml)` is the Back and Start over row under it, so a user who sees an item can go back and change an answer. `knownHtml(summary)` is the items of the "Your policies" panel. Everything from the catalog or engine goes through `esc()`. The screen key (`data-ovl-key`) is the section, its place, its total and its question ids; Q1's key has no total, so ticking policies patches the screen in place instead of drawing it again.
- `dom.mjs` (takes every element or browser object as an argument; no storage, timers or network). `patchOverlapScreen(stage, sections, screenId, stackVm?)` updates pressed state, Continue and the hint in place when the screen's key is unchanged and returns false otherwise; `restoreFocus`, `focusHeading` (focuses the first `[data-focus]`), `copyText(text, { navigator, document }, done)` (clipboard API, textarea + `execCommand` fallback, `done(true|false)` once) and `printList(win)`.
- `app.js` (an ES module; it imports the modules above and `config.mjs`). State is two `let`s, `answers` and `index`. `render()` computes `screenIds(answers)`, clamps `index`, sets `#stage` to the entry screen, an `ovl:<section>` screen or the action list (with the Back and Start over row), sets the progress bar (`bar.style.width`, `aria-valuenow`) from `progressPercent` and rebuilds the "Your policies" panel. `go(n)` sets `index`, renders and moves focus to the new screen's `[data-focus]` heading. One delegated click handler on `#stage`: a button with `data-oq` calls `answer(questionId, optionId)`, which applies `applyAnswer`, emits the analytics `answer` event when the option became selected (Q1 taps count like any other), then patches the screen in place or, when its key changed (a follow-up opened or closed), renders it again and puts focus back on the same option; `data-act` is `next`, `back`, `copy`, `print` or `restart` (Start over resets the analytics run and the answers and goes to the entry screen). The action list is built while its screen renders and emits one `flag_shown` per item. If building the list or the stack drawing throws, a short error panel (or no drawing) replaces it, `console.error` is called and the rest of the page keeps working.
- `css/app.css` has the base look (cards, buttons, tags, the sticky foot, light and dark themes), `.oq*`, `.ovl-foot`, `.al-*`, `.vh` (visually hidden), `.tag.raise` / `.tag.drop` / `.tag.question` (Raise like the red status colour, Drop like the purple one, Question like the blue one, with the word in the tag, never colour alone), `.known`, the entry icons' tilts, the stack drawing (`.stk*`) and an `@media print` block that hides everything except `.actionlist`, forces a light palette, avoids breaking an item across pages and prints each link's address. Option controls are at least 44px tall; unselected option borders use `--muted` (at least 3:1) and a selected option shows a check mark in text. A script lists the stylesheet's selectors that match nothing the page can produce (DECISIONS R1-9); `tests/ui/screens.test.mjs` and `tests/ui/stackView.test.mjs` check the contrast of the pairs used (4.5:1 for words, 3:1 for graphics) in light and dark by reading the palette from the CSS.
- Tests: `tests/ui/viewModel.test.mjs`, `tests/ui/screens.test.mjs`, `tests/ui/dom.test.mjs`, `tests/ui/no-storage.test.mjs` (no `localStorage`, `sessionStorage`, `indexedDB` or `document.cookie` in `index.html` or any module it loads, found by following its imports), and the browser goldens in `tests/browser/` (32 scenarios, 351 screens).

## Liability stack drawing (S14)
One reusable component draws the engine's LiabilityStack (the umbrella on top, the liability limits of the policies under it, and whether each meets what the umbrella asks for). It is driven **only by the model**: `stackViewModel(stack)` reads `stack.umbrella`, `stack.layers` and `stack.attachmentNote` and nothing else (not the answers, not the host state, not the flags; it counts the rows itself instead of reading `counts`, and does not read `findings`).

- **`js/overlap-ui/stackView.mjs`** (pure; no imports at all; a test scans the source for forbidden globals, imports and `style=`). `stackViewModel(stack)` returns `null` when there is no stack (no umbrella), else `{ version, heading, note, rows, counts, layerCount, emptyNote, ariaSummary }`. `rows[0]` is the umbrella; `rows[1..]` are the layers in the model's order (auto, home, motorcycle, boat). A row is `{ id, kind: 'umbrella'|'layer', label, limitCaption, limitLabel, requiredCaption, requiredLabel, status, statusLabel, sentence, detail, icon, bar }`. `status` is the model's `ok | below_required | above_required | unknown` (null on the umbrella row); `sentence` comes from the closed list `STATUS_SENTENCES` ("Meets what your umbrella asks for", "Below what your umbrella asks for. Ask your insurer to raise it.", "Higher than your umbrella requires", "We need one more answer to check this"); `detail` is the model's own `summary` and only for an `unknown` layer where an answer was Not sure or unreadable; `icon` is `umbrella | check | down | up | question`. `emptyNote` is set when the umbrella has nothing underneath. `ariaSummary` is one plain sentence for a screen reader (the umbrella size, then each layer's verdict in words).
- **Bars.** `bar = { kind: 'cap'|'compare', basis: 'amount'|'perPerson'|'perAccident', limitPct, requiredPct, ceiling }`. Percentages (0 to 100, one decimal) of one track **shared by every layer**: scale = the largest number any bar or marker needs times 1.1 (so a marker is never clipped); a non-zero limit is at least 1.5; `null` when that number is not known (Not sure, not answered, unreadable), so nothing is invented. The fill is the limit and a tick marks what the umbrella asks for. For a split limit one number has to be drawn: it is the number the model's verdict was decided on (the lower one for `below_required`, the higher for `above_required`, per accident otherwise), so a bar never contradicts its sentence (250/500 against 500/500 is below on per person only). A "Lower than ..." limit is a ceiling: drawn as a dashed outline, an upper bound, not an exact length. The umbrella row is a full-width **cap**, not a length on the layers' scale: an umbrella does not add to a layer's limit and the model deliberately has no "total protection" figure (DECISIONS S6-2).
- **`stackViewHtml(vm, { idPrefix? })`** returns one `<section class="stk" aria-labelledby>`: an `h3` (`Your umbrella and what sits under it`; the page never says "liability stack"), the model's attachment note, then an `<ol class="stk-rows">`, one `<li>` per row with an icon, the name, the status sentence, an SVG bar (aria-hidden; widths are SVG attributes, so there is no `style` attribute and a strict CSP is fine), and a `<dl>` with both numbers (the limit, and "Your umbrella asks for"). Status is always words plus a distinct icon outline (circle with a check, square with a down arrow, diamond with an up arrow, dashed circle with a question mark), never colour alone. Everything is escaped.
- **Where it is drawn.** (a) On the `ovl:umbrella_stack` and `ovl:umbrella_vehicles` screens (`STACK_SECTION_IDS` in `viewModel.mjs`), below the questions and above the hint and Continue, and redrawn in place after every tap. The whole stack is drawn on both screens, so a motorcycle or boat layer that is asked on the second screen reads "We need one more answer to check this" on the first. (b) In the action list when the household holds an umbrella: directly above the first group that holds an umbrella item (an item whose id starts with `umbrella-`; this includes the motorcycle and boat Raise flags), above the first group when none fired, below the empty-state message for an empty list. It is inside `.actionlist`, so it prints. It is not part of the copied text (`actionListText` is unchanged).
- **Glue.** `viewModel.mjs` adds `liabilityStackModel(answers, catalog?)` (the engine's stack for the answers as a fresh plain object, or `null`; only the context is built, no flags are evaluated), `stackForScreen(answers, screenId, catalog?)` (that model on the two screens above, else `null`) and `STACK_SECTION_IDS`. `screens.mjs`: `overlapScreenHtml(sections, screenId, backHtml, stackVm?)` and `actionListHtml(vm, counting, stackVm?)` (`counting` is S15's privacy-line flag; the stack is the third argument) take the optional view-model (omitted or `null` gives exactly the old markup); `stackBodyHtml(stackVm)` and `stackLiveText(stackVm)` are what `dom.mjs` writes. On a screen the drawing sits in `<div id="stk-body" aria-live="off">` beside `<p class="vh" id="stk-live" role="status">`, which already holds the summary when the screen is drawn. `#stage` is a polite live region (`index.html`), so the drawing is `aria-live="off"` to keep a tap from reading the whole stack aloud, and the status element is rewritten only when its sentence changed. `dom.mjs`: `patchOverlapScreen(stage, sections, screenId, stackVm?)` replaces `#stk-body` and updates `#stk-live`, and returns false (changing nothing) when the page has a drawing and the caller wants none, or the other way round. `app.js`: `stackFor(id)` builds the view-model for a screen or for the action list (in its own try/catch with `console.error`, so a failure leaves the rest of the screen working).
- **CSS** (`css/app.css`, "The umbrella and the limits under it"): `.stk*` rules reusing the status palette (`--ok`, `--under`, `--info`, `--muted`, `--accent`), a 375px rule, and print rules (rows kept together). A test reads the palette from the CSS and checks every status colour clears 3:1 against the card and the empty track in light and dark, and the words 4.5:1.
- **Tests.** `tests/ui/stackView.test.mjs` (view-model matrix over the S6 inputs: the 1,200-combination ladder and every motorcycle and boat limit, the eight named S6 households, hand-made models for shapes the catalog cannot produce; determinism and purity; markup; the screens and action-list placement; `patchOverlapScreen`; the CSS), `tests/snapshots/stack-view.snap.mjs` (view-model and markup for the eight S6 households, built by `builders/stackView.mjs`), and `tests/browser/golden-shape.test.mjs` (Story S14 tests on the goldens). Browser goldens: the umbrella scenarios of `tests/browser/` record the drawing after each answer on the two limit screens and in the list (`tests/browser/README.md`).

## Analytics (S15)
Anonymous answer counting through a provider-pluggable adapter, switched OFF by default, plus the CSP that backs the promise. What is sent, when, and what stops anything else being sent.

**Files.** `public/js/config.mjs` (`ANALYTICS_CONFIG`, plain data), `public/js/overlap-ui/analytics.mjs` (the adapter), the wiring in `public/js/app.js`, `public/_headers` (the headers), `scripts/serve.py` (a local server that applies them), `tests/ui/analytics.test.mjs`.

**Settings (`js/config.mjs`).** `{ provider: 'none' | 'plausible' | 'fathom' | 'zaraz', plausible: { domain }, fathom: { siteId }, zaraz: {} }`; the default provider is `'none'`. `resolveProvider(config)` turns it into `{ provider, scriptUrl, attrs }` and fails closed: an unknown provider, or a missing or malformed site name (a bare host for Plausible, letters and digits for Fathom), becomes `'none'`. The script address is not a setting: `PROVIDER_SCRIPTS` fixes it per provider (`https://plausible.io/js/script.js`, `https://cdn.usefathom.com/script.js`, and none for Zaraz, which Cloudflare adds itself), so an edited setting cannot point the page at another script. `isCounting(config)` is true when a usable provider is set.

**Events.** `buildEvent(name, payload, catalog)` returns a frozen `{ name, label }` or `null` (it never throws; `catalog` defaults to the real one and tests pass a fixture). `checkEvent(event, catalog)` re-validates an already-built `{ name, label }`.

| name | payload | label | rule |
|---|---|---|---|
| `answer` | `{ questionId, optionId }` | `questionId=optionId` | both strings in the shape of an id, the question is in the catalog and is a closed list (single or multi, with options), the option is one of its options, or `not_sure` where the question offers it |
| `flag_shown` | `{ flagId }` | the flag id | a string in the shape of an id that is a flag in the catalog |
| `list_copied`, `list_printed` | none (`undefined`, `null` or `{}`) | `''` | nothing else is accepted |

Anything else returns `null`: another name, extra keys (an identifier, a time, a count, text), a number or a sentence where an id belongs (the id shapes are `[a-z0-9_]{1,64}` for questions and options and `[a-z0-9-]{1,64}` for flags, applied on top of the catalog lookup), an id the catalog lacks, an option of another question. Adequacy and cushion answers (`umbrella_exposure`, `emergency_cushion`, `deductible_*`) are band questions, so only a band id can be sent, never a figure. No timing, tap count or typed text can be named: none of it is in the catalog, and the page has nothing to type.

**Tracker.** `createTracker({ config, catalog, env: { window, document } })` returns `{ provider, counting, state(), start(), track(event), emit(name, payload), reset() }`; `startAnalytics(env, config, catalog)` is `createTracker` plus `start()`. The module reads no global: the browser objects arrive in `env`, so it loads and tests under jsc. Rules: with `'none'` every method does nothing (state `'off'`, no element added, nothing listened to); `start()` adds ONE `<script>` (the fixed address, `defer`, plus `data-domain` or `data-site`) and only for a provider that has a script; an event is passed to the provider only after that script's `onload` (events before it are queued, at most 100; an `onerror`, such as a CSP refusal or an ad blocker, ends counting quietly: state `'failed'`, queue dropped, nothing thrown); Zaraz has no script, so it is called whenever `window.zaraz.track` exists; `track` re-checks every event with `checkEvent`; the same event is counted once per run (`reset()`, called by Start over, begins a new run), so repeating a tap or reaching the list twice does not count twice and tap counts cannot be read from the totals; a provider function that throws is swallowed. Call shapes: Plausible `plausible(name, { props: { label } })`, Fathom `fathom.trackEvent(name + ':' + label)`, Zaraz `zaraz.track(name, { label })`; an event with no label is sent by name alone.

**Where `app.js` emits** (`analytics = startAnalytics({ window, document }, ANALYTICS_CONFIG)`): `answer` from `answer(questionId, optionId)` when a tap on an option makes it selected (`becameSelected(before, after, q, o)`: unticking, or tapping the chosen one again, is not a new answer; a Q1 tap is an `answer` like any other, with the question `policies`); `flag_shown` for each flag in the action list view-model when the list screen renders it (`flagIdsOf(vm)`); `list_copied` after a successful copy; `list_printed` when Print is used; `analytics.reset()` on Start over. A test pins that app.js passes the counter nothing but these (no answers object, screen index or clock in any event; the answer event is built from the tapped button's `data-oq` and `data-ov` only).

**Privacy statements (`screens.mjs`).** The page shows `privacyLine(analytics.counting)`: with nothing counted, `PRIVACY_LINE_NONE` (answers stay on the page and are not saved, nothing is counted or sent); with a provider, `PRIVACY_LINE_COUNTING` (answers are counted anonymously: which options were chosen and visits, never who you are, no cookies, never stored against a person; the page has nothing to type, so no names, numbers or other details are sent). It appears on the entry screen with `ENTRY_NOTE` (general information, not advice, not a licensed agent or broker), via `entryNoteHtml(counting)`, and at the foot of the action list (`actionListHtml(vm, counting)`, `actionListErrorHtml(counting)`). The page must never claim counting that is not happening, which is why the line follows the setting (DECISIONS S15-1). The brand line in `index.html` says only what is true in both settings.

**Headers (`public/_headers`, Cloudflare Pages format).** One rule, `/*`: `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`. `style-src` is `'self'` alone because the page writes no `style="..."` attribute and has no `<style>` block (DECISIONS R1-8); a test pins that. With a provider chosen, its hosts are added per `PROVIDER_CSP` in `analytics.mjs`, which a test keeps equal to `public/_headers`, `js/config.mjs` and the table in `docs/OPEN-ITEMS.md` S15-1 (Plausible: `https://plausible.io` in `script-src` and `connect-src`; Fathom: `https://cdn.usefathom.com` in `script-src`, plus `connect-src` and `img-src` as an unconfirmed precaution; Zaraz: none).

**Local check (`scripts/serve.py`).** `python3 scripts/serve.py [DIRECTORY] [--port N]` (default the repo's `public` folder, port 8766) serves static files with the headers of `DIRECTORY/_headers`: path patterns with `*` and `:name`, several matching rules combined, duplicate headers joined with a comma, `! Name` to remove one, `_headers` itself answered 404, `Cache-Control: no-cache` unless the rules set one. `--check /path` prints the headers a path would get; `--self-test` checks the parser. Python 3.9, standard library only. `npm run preview` and `scripts/serve.sh` do not apply `_headers`. The golden test cannot run behind the policy (`frame-ancestors 'none'` blocks its same-origin iframe), so it uses a plain static server.

**Tests (`tests/ui/analytics.test.mjs`).** Every refusal path of the allowlist, labels only from the catalog (every real question/option pair and every flag), band-only adequacy and cushion, provider `'none'` sends and loads nothing with fake provider functions on the page, each provider's call shape and the load-then-send order with fakes, fail-closed settings, one count per run, a source scan of everything the page loads (index.html plus every module reachable from it: no `fetch`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`, dynamic `import()`, tracking pixel, storage or cookie; the provider loader is the only code that adds a script element; no inline script, handler attribute or third-party address in the shell; no `@import` or remote `url()` in the stylesheet), the CSP (no third-party host while the provider is `'none'`, the provider table covers all three providers and matches the OPEN-ITEMS table and `public/_headers`), and the page statements, including that the recorded goldens carry the privacy line for the configured setting.

## Rules for changing the project
The build ran as parallel stories in separate git worktrees, merged to `main` one at a time (rebase, full suite, fast-forward). The rules that kept that safe are the rules for any change.
- Own your files: a change edits the files its subject names, and the shared append-only logs (`docs/DECISIONS.md`, `docs/OPEN-ITEMS.md`) use git's union merge (see `.gitattributes`). Number new entries with a story or change id (for example `S16-1`), never the next global D-number.
- Flag files are per domain (`flags/{umbrella,umbrellaScope,vehicles,auto,home,renters,health,deductible,other}.mjs`); `flags/index.mjs` concatenates all nine and is not edited for a new flag in an existing file.
- Data module export contract (what `data/catalog.mjs` imports): `questions/index.mjs` exports named `QUESTIONS` (array, display order) and `SECTIONS` (ordered `[{ id, title, reason, showIf }]`); `sources.mjs` exports named `SOURCES` (object keyed by id); `cards.mjs` exports named `CARDS` (object keyed by id; extra helper exports are fine); each `flags/<domain>.mjs` has an array as its **default** export. A change that replaces one of these files keeps that export shape (a default export alongside the named one is harmless). `catalog.mjs` and `flags/index.mjs` are not edited.
- `tests/engine/purity.test.mjs` scans every module reachable from the engine files and `data/catalog.mjs` for forbidden globals (DOM, Node, `URL`, `console`, timers, `structuredClone`, `fetch`, `Date`, `Math.random`, `Intl`), non-relative or non-`.mjs` imports; new data files are covered automatically once the catalog imports them.

## Conventions
- IDs: questions/options `snake_case`; flags/sources/cards `kebab-case`.
- Copy: plain language, second person, jargon defined in a clause, matches the voice of the page: it reads like a friend asking, not a form, and no internal or interface language leaks into copy. No "home equity", "next screen", "generic patterns".
- Dates: ISO `YYYY-MM-DD`; `lastVerified` is the day the page was actually fetched and read.
- Every change: tests added; `scripts/test.sh` green; the browser goldens replayed (and re-recorded, deliberately, for anything a user reads); `docs/DECISIONS.md` updated for any deviation; `docs/TRACEABILITY.md` updated for any SPEC requirement it touches. Nothing here deploys: `npm run deploy` is the owner's (OPEN-ITEMS S16-4).
